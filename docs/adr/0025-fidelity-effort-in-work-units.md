# 0025 — Fidelity effort is declared in work units, not wall-clock

A03's three-arm query comparison finished with two usable results in the learned arm, two in the random arm and **zero** in the uncertainty arm, whose native command returned 2 with `insufficient_completed_evidence`. The task blocker attributed this to "startup/deadline overhead within original budgets". That attribution was incomplete, and the comparison was not merely weak — it was invalid.

All three arms share one frozen initial design, because `Limits.seed` and `BOUNDS` are identical, so the first twelve candidates are byte-identical across arms. Ordinal 6 (`candidate_id` `fba7c09c65…`) was executed in all three with identical declared parameters and `timeout_s=120`. The learned arm recorded four feasible plans, each doing **24 candidate evaluations and 128 completed integrations** with worker wall times of 0.548–0.840 s, and the case completed. The random arm's plan-0 did the **same 24/128 work** in 1.325 s and was feasible; its plan-1 was killed at `wall_s=6.024`. The uncertainty arm's plan-0 was killed at `wall_s=6.037` before reporting counters. The three arms ran strictly sequentially (UTC 06:08:51→06:16:33, 06:17:15→06:24:40, 06:25:05→06:31:26), so this is not mutual CPU contention; it is background host load swinging identical deterministic work from 0.55 s to more than 6 s.

`map_policy` declared `wall_budget_s` of 6.0 for low and 15.0 for high fidelity, and `_solve` tested that budget inside the work loop at every solver boundary. The declared work budget (`max_iterations`, `max_candidate_evaluations`) therefore never got to terminate the search: a wall-clock guard pre-empted it whenever the host was loaded. The training **label became a function of machine load rather than of the candidate**, and because one flip decides whether `search.best()` is empty, it decided each arm's exit code. The uncertainty arm's zero usable results measured that host's load curve over 22 minutes, not the query strategy.

Fidelity is now declared by work units only. `wall_budget_s` becomes a single host resource backstop of 25 s for both fidelities, and `map_policy` asserts `WALL_BACKSTOP_S * EXECUTION_STEPS <= PER_QUERY_TIMEOUT_S - CASE_OVERHEAD_RESERVE_S` (4 × 25 ≤ 120 − 8) so the backstop provably cannot pre-empt the per-query budget that `configs/execution.yaml` declares. The incumbent-acceptance guard in `plan` and `_solve` is restated in the work units that actually define the low budget (`max_iterations == 1 and max_candidate_evaluations <= 24`); its `wall_budget_s <= 6.` clause is removed because a guard that flips with host load turns one candidate into two different scientific labels. The guard's intent — incumbent acceptance only under the declared low computation budget — is unchanged.

Unchanged and explicitly verified as unchanged: `max_iterations` 1/25, `max_candidate_evaluations` 24/120, per-query timeout 120 s, batch wall 1800 s, 8 GiB memory limit, 12 initial points, 24 iterations, 24 high-fidelity calls, the physical model, action admission, `tell()` validation, UNKNOWN semantics, and every acceptance criterion in `TASKS.yaml`. No target proposition was weakened and no acceptance script was made unconditionally successful. A genuine outer timeout still yields UNKNOWN with no invented label.

Verification used two new tools rather than assertion. `tools/diagnose_a03_label_determinism_20261016.py` is read-only over sealed arm artifacts and returned exit 1 with `divergent_ordinals=[6]`, reproducing the finding from evidence alone. `tools/probe_a03_label_determinism_20261016.py` re-executes one sealed candidate repeatedly through the real owned oracle worker. After the repair, low-fidelity ordinal 6 returned `completed` on **5 of 5** repetitions with identical utility `3.0302705698157835e-09`, identical work counters and worker wall times of 0.911–1.444 s against the 25 s backstop; high-fidelity ordinal 12 returned `completed` on **3 of 3** with identical utility `1.2052483836389859e-08`, identical margin `-1e-12` and an identical per-step work sequence `[(25,132),(27,140),(27,140),(40,192)]`. `tests/integration/test_learning_budget.py` returned 12 passed, exit 0.

Two defects in the probe itself were found and are recorded rather than hidden. Its first version passed vacuously: the calibration packet is bound to the ROOT code hash, so after the source edit the sealed packet was correctly refused, all five repetitions returned `unknown`, and the probe scored that agreement as reproducibility with exit 0. It now returns exit 2 whenever no repetition reached the planner. Its second version falsely flagged high fidelity because it flattened per-step counters into a set, so the legitimate difference between the four MPC steps of one execution looked like disagreement between repetitions; it now compares per-step sequences. The first-failure artifacts are preserved at `artifacts/a03-determinism-probe-20261016-a`, `-b` and `-d`.

Scope of the claim: identical candidate, fidelity and work budget give an identical label **whenever the host completes the declared work inside the per-query timeout**. This is not a proof that the three arms are now comparable, and it grants no advantage claim for any query strategy. The arms have not been re-run on the repaired source, so **A03 remains in_progress** and the previous 2/2/0 result stays on record as an invalid comparison rather than being overwritten. Because `code_hash(ROOT)` and the learning `implementation_hashes` changed, all three arms must be re-run serially on one frozen source before any comparison is recorded.
